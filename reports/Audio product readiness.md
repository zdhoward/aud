# Make aud a dependable audio reference

aud has a useful architecture and a substantial test baseline, but it needs a safety and fidelity pass before it becomes the reference implementation for a language port. The immediate priorities are predictable selection, validated execution plans, safe writes, metadata preservation, and explicit encoding behavior. General naming profiles can cover the requested conventions through templates and configurable transformations, without community-specific APIs or product labels. The existing roadmap already identifies much of the work; its sequence should change so that the audio engine contract precedes performance restructuring and new interfaces. **Finish the Python product around observable guarantees, then port those guarantees.** This report proposes work packages and acceptance gates; it does not mark features shipped or change existing release milestones.

## Safe plans should become the shared execution contract

**Work package A should make every operation explainable before it writes.** Extend the plan from per-file input/output pairs into a serializable batch description: selected inputs, grouped operations, all destinations, effective audio settings, validation findings, collision decisions, and required tools. Joins need explicit many-to-one relationships rather than repeated per-file pairs pointing at the same destination. Preview must use the same resolved plan as execution and must not consume counters, modify files, or silently select different inputs. Add structured results for success, skip, failure, and cancellation, including the operation and affected paths. Existing boolean methods can remain compatibility wrappers while a richer interface develops. ([Current plan](../aud/core/plan.py), [Join execution](../aud/core/adapters/audio.py), [Roadmap](../ROADMAP.md))

Use overwrite policy `error` by default, with explicit `skip`, `overwrite`, and deterministic `auto-rename` alternatives. Preflight must catch duplicate destinations, source/destination identity, intermediate-name collisions, reserved names, invalid separators, and directory traversal. Detect collisions after filename sanitization, Unicode normalization, and case folding under the selected portability policy. Scan symlinks only through explicit configuration, and state recursion and containment rules. Resolve the allowlist/extension interaction and document whether selection conditions intersect; introduce the common-audio default with a compatibility note. Full-match regex behavior, glob support, custom selection policies, and metadata filters should build on these defined semantics. ([Safety issue #42](https://github.com/zdhoward/aud/issues/42), [Symlink issue #43](https://github.com/zdhoward/aud/issues/43), [Filesystem adapter](../aud/core/adapters/filesystem.py))

For audio replacement, write a uniquely owned temporary file beside the destination, validate it, then commit the replacement with the platform's appropriate rename/replace mechanism. Cleanup must remove only temporaries created by that run. Recheck destination conditions at commit time and define race behavior; preflight alone is insufficient. Preserve the original when decoding, encoding, validation, or cancellation fails. Cross-filesystem moves and ancillary-file copies need their own documented commit rules. Do not promise a whole batch is atomic: expose exactly which files committed and which failed. Tests should inject encoder failure, interruption, collision, and permission errors and verify original bytes and temporary cleanup.

This package also closes the practical foundation gaps: actionable FFmpeg/ffprobe checks, standard library logging with a `NullHandler`, automatic operation audit records, newline-safe log messages, and log paths resolved relative to the working directory. Harden fixtures under #54/#65/#66: generate project-owned synthetic audio, use roughly four-second assets where watermark behavior needs time, and keep very short assets for focused checks. Assert sample properties, amplitude/duration changes, tags, and preserved bytes instead of return values. Add Windows CI and include OS in artifact names. Property tests should cover deterministic naming, collision handling, and valid Unicode transformations; **uppercase/lowercase round trips are not universally reversible**. ([Fixture issue #54](https://github.com/zdhoward/aud/issues/54), [Filename coverage #65](https://github.com/zdhoward/aud/issues/65), [Testing and benchmarks #66](https://github.com/zdhoward/aud/issues/66))

## Fidelity requires one engine decision before acceleration

**Work package B should define and implement the audio contract before optimizing it.** Advance the direct-FFmpeg investigation from its current position after the web milestone. First specify probing, ordered effects, output codecs, metadata mappings, cancellation, streaming, and validation; then implement the engine against that contract. This avoids substantial pydub batching work followed by another rewrite of the same execution layer. Registry dispatch and focused facade simplification remain useful when they serve this contract. Add bounded concurrency only after serial execution passes failure and fidelity tests, with measured throughput and memory limits. ([Engine issue #62](https://github.com/zdhoward/aud/issues/62), [Core simplification #64](https://github.com/zdhoward/aud/issues/64), [Batching #44](https://github.com/zdhoward/aud/issues/44), [Parallelism #45](https://github.com/zdhoward/aud/issues/45))

The current dependency imports `audioop`, which Python removed in 3.13; the present dependency configuration therefore does not support that runtime. This does not mean Python 3.13 support is categorically impossible. A compatibility dependency such as `audioop-lts` is a possible temporary bridge if maintaining the existing engine helps deliver an urgent fix, but it should not become a prerequisite for the new engine. Direct execution also enables explicit 24-bit output and processing without loading entire long files into Python memory. An internal engine migration alone does not require a major release; assign SemVer based on actual public compatibility, and keep version, tag, release, changelog, and package publication aligned. ([Python audioop removal](https://docs.python.org/3/library/audioop.html), [Current conversion limits](../aud/core/adapters/convert.py), [Release policy](../ROADMAP.md))

Offer neutral encoding profiles such as archival FLAC, MP3 V0, MP3 320 CBR, and optionally MP3 V2. Record encoder version and effective arguments, distinguish VBR quality from bitrate, and validate supported sample rates/channels before execution. Preserve source sample rate, bit depth, channels, and decoded samples for preservation operations; resampling, channel conversion, gain, and normalization create processed derivatives. FLAC compression level changes compression effort rather than fidelity. Keep peak-normalization headroom and units explicit, and distinguish this operation from loudness processing measured in LUFS. ([LAME usage](https://svn.code.sf.net/p/lame/svn/trunk/lame/USAGE), [FLAC tools](https://xiph.org/flac/documentation_tools_flac.html), [Normalization implementation](../aud/core/adapters/audio.py))

Preservation profiles should reject known lossy reencoding unless explicitly requested, while generic conversion can legitimately produce PCM from lossy input for editing or compatibility. Such conversion cannot restore lost information and must not claim a quality upgrade. Canonical metadata must cover artist, album artist, album, title, year, track/disc numbers and totals, artwork, and a documented unknown-tag policy across ID3 and Vorbis comments. Tag-only edits must avoid audio reencoding. Acceptance requires tagged MP3/FLAC fixtures, 16/24-bit PCM comparisons for lossless paths, inspected MP3 settings, and a demonstrated single final encode for a chain. ([Conversion reference](https://interviewfor.red/en/transcodes.html), [Format reference](https://interviewfor.red/en/formats.html))

## Naming profiles should prepare complete output packages

**Work package C replaces the proposed specialized naming feature with reusable naming profiles.** A profile combines a directory template, filename template, transformations, missing-field policy, and portability policy over canonical metadata. Proposed defaults could render `{album_artist} - {album} ({year}) [{encoding_profile}]` and `{disc_number}-{track_number:02} - {title}`. Support optional transliteration, uppercase, underscores, configurable separators, affixes, zero padding, and disc-aware numbering. Preserve Unicode by default and retain original metadata independently of sanitized filenames. Missing required fields should stop planning rather than invent artist, year, edition, source, or suffix values. ([Naming issue #63](https://github.com/zdhoward/aud/issues/63), [Reference tags and folders](https://interviewfor.red/en/rules.html))

These templates are product proposals, not a universal standard extracted from the reference. Filename parsing should accept an explicit grammar or configured profile, produce candidate field values and ambiguity/confidence findings, and require deliberate application before modifying tags. A real album fixture must preview its entire destination tree, including multidisc order, absent metadata, Unicode, case collisions, and affixes. Documentation should show configuration examples and explain when metadata must be supplied manually. This delivers the requested naming flexibility without coupling the API to a particular community.

Prepare audio together with original logs, artwork, cues, checksums, and a processing manifest. Start with sidecar inventory and byte-preserving copies. Original extraction logs must remain immutable; derived reports must identify their own origin. Validate cue targets, containment, track/index relationships, and renamed-file mappings; preserve original cues and identify any rewritten cue as derived. Separate declared source provenance, codec inspection, decoder integrity, PCM equivalence, extraction claims, and human review. Optional spectrograms can support inspection with recorded settings, but frequency cutoffs cannot certify a file's complete conversion history. Full extraction-log scoring and disc-image splitting need separate specifications and corpus tests. ([Ripping reference](https://interviewfor.red/en/ripping.html), [Sample log](https://interviewfor.red/en/log.html), [Sample cue](https://interviewfor.red/en/cue.html), [Audacity spectrum documentation](https://manual.audacityteam.org/man/plot_spectrum.html))

## Security review should follow the actual trust boundaries

**Work package S adds a security audit before the port readiness gate.** Start with a source-first pass over the current library and packaging, so findings can inform safe execution design. Repeat the affected checks after the FFmpeg engine, naming/sidecar handling, and CLI land, then independently verify findings against the release candidate. This is planned work, not a completed audit or a security certification. Distinguish trusted caller-selected paths from untrusted filenames, metadata, profiles, cues, logs, artwork, and media decoded by external tools. Record which principal and resource each boundary protects; do not classify intentional library access to a caller-selected directory as a vulnerability merely because it is outside the working directory.

Review path traversal, absolute/drive/UNC paths, symlink and Windows junction escapes, hard-link behavior, destination races, unsafe replacement, and temporary-file cleanup. Check cue and naming-template paths against the documented output/root policy. Review FFmpeg/ffprobe invocation for argument and option injection, shell use, executable resolution, unexpected network/protocol access, inherited environment, timeouts, process cleanup, and resource limits. Treat corrupt media, oversized artwork/tags, pathological regexes, and excessive concurrency as bounded-resource cases. Inspect log/report handling for forged entries or unintended sensitive-path disclosure, and ensure any eventual HTML interface escapes metadata and enforces its root and local-access policy.

Audit Python dependencies, external codec-tool versions, installed package contents, accidental secrets, and CI/release permissions and publishing inputs. Use current authoritative advisories when the pass runs; a scanner result alone is not proof that aud is affected. The future web UI needs a separate exposure review before it ships, including request validation, job authorization, cross-origin requests, and access to local files. Existing CodeQL automation contributes evidence but does not replace review of these product-specific boundaries. ([Security policy](../SECURITY.md), [CodeQL configuration](../.github/workflows/codeql.yml), [Publishing workflow](../.github/workflows/publish.yml))

The audit deliverable must identify the reviewed commit, threat model, covered surfaces, excluded surfaces, source evidence, and remaining validation gaps. Each candidate needs an affected principal/resource, concrete security outcome, safe reproduction where feasible, and the smallest effective fix. Confirmed findings require independent verification; unresolved candidates remain clearly labeled as needing validation. Run adversarial fixtures only in an OS-enforced sandbox with no external network, an allowlisted environment, read-only source/toolchain, scratch-only writes, and CPU/memory/process/disk/time limits. If those controls are unavailable, retain source evidence and a validation plan instead of executing the target. The release gate requires all confirmed high/critical findings fixed and rechecked, with lower-priority findings and validation gaps explicitly triaged and any accepted residual risk documented.

## The CLI and conformance corpus define the port gate

**Work package D builds the real CLI over the shared contracts.** Provide list/inspect, convert, rename, effects, and export commands with configuration files, human-readable previews, JSON dry runs, progress, cancellation, stable exit codes, and machine-readable results. CLI defaults must match the Python API. Package a working installation with FFmpeg guidance, supported Python versions, generated API documentation, and tested playbooks for preservation, listening copies, album naming, and recovery from partial failure. Complete #49/#54/#56/#67 alongside these interfaces. Trusted publishing and branch protection remain maintainer settings actions under #71/#69; verification of private vulnerability reporting also belongs in release readiness. ([CLI milestone](../ROADMAP.md), [Documentation #67](https://github.com/zdhoward/aud/issues/67), [Publishing #71](https://github.com/zdhoward/aud/issues/71), [Branch protection #69](https://github.com/zdhoward/aud/issues/69))

**Work package E freezes observable behavior for the port.** The completion checklist is a clean wheel/sdist installation; safe-write and collision tests; metadata/artwork preservation; verified lossless properties; explicit lossy settings; naming and sidecar package fixtures; matching preview/execution destinations; serial/concurrent equivalence; cancellation and partial-failure results; documented limits; a passing supported-platform matrix; and the security audit gate in work package S. Store versioned JSON plan/result schemas and project-owned input/output expectations. Compare lossless decoded samples where appropriate, lossy output properties within tolerances, and deterministic naming exactly. Do not demand identical lossy bytes across encoder versions without controlling those versions.

The first implementation slice should reproduce the observed selection, tagged-MP3, same-file export, and collision problems, then land safe selection/writes with regression fixtures. The second should ship the shared plan/result contract and a narrow direct-FFmpeg vertical slice with canonical metadata and encoding profiles. The third should implement naming templates and one complete album export package, then expose it through CLI dry-run and execution. Keep the optional web interface, plugins, video generation, and distribution integration outside this pre-port gate. They can reuse a dependable core later without delaying the reference product.

## Conclusion

The useful boundary for the language experiment is a documented behavior contract backed by fixtures, not completion of every historical idea. A port should inherit intentional decisions about selection, naming, fidelity, and partial failure rather than accidentally reproduce adapter quirks. Shipping these contracts in Python first also makes future interfaces and engine changes smaller: each can demonstrate that it preserves the same user-visible guarantees.
